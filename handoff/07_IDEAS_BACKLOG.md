### INN-41 · In-house reference specimen control chart (score 4.0)
**Pitch:** the lab keeps one polished "check coupon" of known grain size; measuring it weekly produces an individuals/moving-range (I-MR) control chart that proves the *whole method* (prep-free re-image → detection → G) is stable. **User story:** As a lab technician, I image our reference coupon on Monday morning, click "Log as control run", and see a green "method in control" chip on every report that week. **Why:** INN-29 proves the SEM scale; this proves the *measurement result*. ISO 17025 §7.7.1 ("ensuring the validity of results" — regular use of reference materials, control charts) and a standard auditor question. Zeiss/Clemex sell GxP storage but no built-in control charting of a check specimen. **Spec:** Settings → "Reference specimens" (optional, default off): name, nominal G (user-entered or established from first 10 runs), preset used. A control run is an ordinary analysed session tagged `control_of=<specimen id>`; its G is appended to `workspace/_control/<specimen>.jsonl` (stdlib JSON, no Qt, new `data/control_records.py`). `core/control_chart.py` computes centre line, UCL/LCL = mean ± 2.66·MR̄, and flags Western Electric rules 1 (1 point beyond 3σ), 2 (9 on one side), 3 (6 trending). UI: chart on Settings page + status chip beside the INN-29 calibration chip ("Control: in control, last run 3 d ago" / amber "out of control since 22 Sep" / grey "not set up"). Reports print the chip text in the methods block; never block export. **Acceptance:** with 20 synthetic control Gs ~ N(7.0, 0.1) the chip is green; appending 7.6 triggers rule 1 and turns it amber; 9 consecutive values at 7.08 trigger rule 2; limits match a hand-calculated I-MR example to 3 dp.

### INN-46 · Field-outlier check on each lot (score 3.6)
**Pitch:** flag the field that doesn't belong before it drags the lot mean. **User story:** As a technician, the lot card tells me "Field 4 (G 9.1) is an outlier vs the other 5 (G 7.3 ± 0.2) — check focus/etch/location" and offers "exclude from lot" with a reason. **Why:** one bad field (edge of specimen, decarburised layer, smeared prep) is the most common cause of a wrong lot result; E112 CI (INN-27) widens but doesn't say *which* field. Recording the exclusion reason is a traceability win (ISO 9001 §7.5 records). **Spec:** `core/metrics.field_outliers(field_Gs, alpha=0.05)` — two-sided Grubbs test for n ≥ 5 (critical value via `scipy.stats.t`), Dixon Q for n = 3–4, none for n < 3. Lot card shows an amber row marker + tooltip; "Exclude from lot…" requires picking a reason (Out of focus / Prep artefact / Wrong location / Other + text), stored in the session JSON and listed in the report's methods block ("1 field excluded: F4, prep artefact"). Exclusion is reversible; no auto-exclusion ever. Default on (advisory only). **Acceptance:** Gs [7.2, 7.3, 7.4, 7.3, 7.2, 9.1] flag index 5 at α = 0.05; [7.2, 7.3, 7.4, 7.3, 7.2, 7.5] flag nothing; excluded field disappears from lot mean/CI and appears with its reason in XLSX and PPTX.

### INN-50 · Manual spot-check count (score 3.6)
**Pitch:** the operator counts intercepts by hand on one random test line; the app compares with its own count — skeptics convinced in 60 seconds. **User story:** As a senior metallographer who distrusts AI, I click each grain-boundary crossing on a highlighted line and the app says "You: 23, App: 24 — agreement 96 %". **Why:** the fastest way to earn trust from people who have hand-counted E112 for 20 years; creates a recorded human cross-check per lot (ISO 17025 §7.7.1 "replicate tests using same or different methods"). Keyence/Clemex show automated counts but no built-in human-vs-machine check. **Spec:** Review page → "Spot check" button: draws one random line (or circle) from `core/astm._line_paths` with a seeded RNG (seed stored), operator clicks crossings (click adds a tick, right-click removes; ½-hit via Shift-click per E112 triple points). Machine count from `core/astm.count_path` on the same path. Result `{seed, path, manual, auto, agreement_pct, operator, time}` saved in session JSON; shown on the lot card ("Spot-checked ✔ 96 %") and in the methods statement. Agreement < 85 % shows amber "review segmentation" hint. Optional; no gating. **Acceptance:** on a synthetic mosaic, clicking exactly the true crossings yields agreement ≥ 95 %; the same seed re-draws the identical path after reload; record appears in XLSX methods text.

### INN-42 · Result fingerprint + one-click re-verify (score 3.6)
**Pitch:** every result carries a fingerprint of *exactly* what produced it; "Re-verify" re-runs silently and confirms the number is reproducible. **User story:** As a lab manager answering a customer query 8 months later, I open the lot, click "Re-verify", and get "Reproduced: G 7.41 (stored 7.41), 312/312 grains" or a clear diff. **Why:** reproducibility is the core of a defensible number (ISO 17025 §7.5 technical records must allow repetition). Lightweight replacement for the cancelled INN-30 seal — no workflow, just evidence. **Spec:** at analysis time store `fingerprint = {image_sha256, params_json_sha256, mode, software_version (version.py), sam_checkpoint_sha256 or "n/a", manual_edits_sha256, calibration_um_per_px}` in the session file (`data/session_io.py`). The results table shows a short 8-char ID (e.g. `fp:3a9c1e07`) printed in reports. "Re-verify" (lot or image context menu) re-runs detection off-thread from the stored params + edits, then compares: grain count, G, mean ECD. Verdict: *Identical*, *Reproduced within tolerance* (|ΔG| ≤ 0.05, count ±1 %, for GPU/CPU float differences), or *Differs* with a table of what changed (e.g. "software 3.0.2 → 3.1.0"). Missing source image → "image moved or deleted" with relink. **Acceptance:** re-verify on an unchanged session returns Identical; altering one param in the JSON returns Differs naming that param; the fingerprint ID appears in the XLSX methods sheet; a renamed image file is detected via SHA even under a new path.

### INN-47 · Image-quality gate on import (score 3.2)
**Pitch:** traffic-light each image for focus, charging, saturation and "enough grains" *before* anyone trusts its number. **User story:** As a technician, a red dot on a thumbnail tells me "blurred (focus score 0.21) — re-image" while I'm still at the SEM. **Why:** garbage-in is the #1 hidden source of wrong G; E112 also expects ≥ ~50 grains per field for planimetric work. No competitor surfaced a pre-analysis quality score. **Spec:** `core/image_quality.py` (no Qt): focus = variance of Laplacian normalised by image intensity variance; saturation = % pixels at 0 or max within the valid mask; charging proxy = % of valid area in bright blobs > 3σ larger than 0.5 % of field; streak/drift = dominant horizontal-line energy from row-mean FFT; grain adequacy = estimated grain count from a cheap Otsu+watershed pre-pass or post-analysis count < 50 → amber. Each metric → green/amber/red with thresholds in Settings (defaults tuned on synthetic fixtures; flagged for real-image tuning, D-13). Thumbnail dot + tooltip listing failing checks; per-image metrics exported in the XLSX image sheet. Advisory only. **Acceptance:** a synthetic mosaic is green; the same mosaic Gaussian-blurred (σ = 4) is red on focus; 10 % saturated pixels → amber saturation; a 20-grain field → amber adequacy; metrics compute in < 150 ms for 2048×1536.

### INN-49 · Acquisition-conditions ledger & comparability warnings (score 3.2)
**Pitch:** record kV, WD, detector, mag and pixel size for every field and warn when lots being compared were imaged differently. **User story:** As QA comparing Lot A and Lot B, I see "Heads-up: Lot B imaged at 5 kV BSE, Lot A at 15 kV SE — contrast differences can shift detected boundaries." **Why:** acquisition drift silently confounds lot-to-lot comparison; auditors ask "were both measured under the same conditions?" (ISO 17025 §7.2 method conditions). The parser already extracts these fields (`SemMetadata`), so this is cheap. **Spec:** persist `SemMetadata.to_dict()` per image in the session (if not already) and aggregate per lot into a conditions summary: modal detector, kV range, WD range, mag range, pixel-size range. ### INN-43 · Lot comparison matrix + equivalence vs a baseline lot (score 2.0)

### INN-48 · Uncertainty budget — GUM-lite expanded U (score 1.4)
**Pitch:** report "G = 7.4 ± 0.3 (U, k = 2)" combining statistical, calibration and segmentation contributions — the number an ISO 17025 assessor actually wants. **User story:** As a lab manager, when a customer asks "how sure are you?" the report has a small budget table showing where the uncertainty comes from. **Why:** ISO 17025 §7.6 requires evaluating measurement uncertainty; INN-27's CI covers only field-to-field scatter. **Spec:** `core/uncertainty.py`: u_stat = SE of lot mean G (INN-27); u_cal = from latest INN-29 calibration error % propagated to G (G depends on log2 of N_A ∝ 1/px², so δG ≈ 2·log2(1+ε) — document derivation); u_seg = half-range of G when re-running one representative field with detection sensitivity ±1 step (reuse INN-42 re-run machinery, off-thread, cached); u_c = root-sum-square, U = 2·u_c. Budget table (source, value, method, share %) in the lot card popover and report methods sheet. Optional (Settings toggle, default off) and labelled "estimate" until method validation (INN-35) with real images. **Acceptance:** with u_stat 0.1, cal error 1 %, seg half-range 0.05 the table reports U = 2·√(0.1² + 0.0287² + 0.05²) ≈ 0.23 to 2 dp; turning the toggle off removes the section from all exports.
